前提
参加する競技のルールを確認し、変更できる範囲、維持すべき機能、採点条件、利用できるリソースを整理する。ルールは競技ごとに異なるため、その競技の規定を優先する。
例えば、URI、HTMLのDOM構造、静的ファイルの内容や画面上の動作を維持する必要がある場合は、それらを変えない方法で高速化する。POST後の即時反映、メンテナンスコマンドとの互換性、再起動後の動作とデータの永続性なども、競技の要件に従って確認する。
許可される場合は、取得するデータやSQLの見直し、インデックスの作成・削除、キャッシュ、DBスキーマの変更などを改善候補にできる。キャッシュや遅延書き込みを使う場合も、即時反映や永続性などの要件を満たす必要がある。

構成を理解する
アプリケーション、Webサーバー、データベース、キャッシュ、外部コマンドなどの構成と依存関係、データの流れを確認する。画面と操作がどのリクエストやサービスを利用するかも把握する。


1. 現状を測る
   ベンチマークのスコアと成功・失敗を記録し、アクセス数・応答時間・SQLの実行回数や時間を確認できるようにする。必要に応じて、アプリケーション内の処理や外部サービスへのアクセスにかかる時間も計測する。
   リクエストを識別できる情報を使って、その処理に対応するログを関連付ける。操作別・処理別の回数や時間を機械的に集計できるようにし、代表的なリクエストも追跡できる状態にする。集計結果はボトルネックの候補として扱い、実行計画やリソースの状態と合わせて原因を確認する。
   詳細な計測は性能に影響するため、計測の有無や実行環境などの条件も記録し、同じ条件で結果を比較する。具体的な計測方法は対象の環境に合わせて用意する。
2. 遅い場所を調べる
   アクセスログから操作ごとのリクエスト数と応答時間を確認し、調べる対象を選ぶ。次に、そのリクエスト内でSQLや外部サービスへのアクセスなどが何回呼ばれ、どれくらい時間を使っているかを調べる。
   時間や回数が目立つ処理について、SQLの実行計画、スロークエリログ、アプリケーションのプロファイルやコードを確認し、遅さの原因について仮説を立てる。応答時間の合計だけで判断せず、CPUやデータベースの状態も合わせて確認する。
   原因を絞れない場合は、構成とデータの流れに立ち戻り、まだ計測できていないサービスや処理を洗い出す。リクエスト全体と計測済み処理の範囲を照合し、必要に応じて外部依存の待ち時間、CPU・メモリ・ディスク・ネットワーク、接続数やキューなどを計測する。時間の差は、処理の重複や計測範囲の違いがあるため、そのまま未計測部分の時間とは決めつけない。計測の負荷と条件も確認したうえで再度候補を絞る。
3. 原因を一つに絞って変える
   例えば「ある画面を表示するたびに、大量のSQLが発行されている」という証拠があれば、その箇所を直す。同じデータの取得や処理が繰り返されていないかを確認し、必要に応じて一括取得やキャッシュなどで回数を減らす。キャッシュを使う場合は更新・初期化・再起動時の整合性を確認する。一度にたくさん変えると、何が効いたか分かりにくくなる。
4. 正しさと速さを再確認する
   変更後にベンチマークを実行し、pass: true を確認してからスコアを比べます。スコアが上がっても、機能が壊れていれば採用できません。
5. 結果を記録して繰り返す
   「何を見て、何を変え、スコアがどう変わったか」を残します。効果がなければ戻し、次の候補を調べます。
